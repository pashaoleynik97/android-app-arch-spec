# 30 — Dependency injection (DI)

Tier: **Core** (component `architecture`). Hilt with KSP. Gotchas that depend on the Hilt/KSP version are in
`toolchain.md` (BUILD-34, BUILD-37, BUILD-40).

Contents: 1. Entry points · 2. Where modules live · 3. Module shape · 4. Qualifiers, scopes, dispatchers ·
5. Collisions and optional sets · 6. Eager singletons · 7. Testing

---

## 1. Entry points

**DI-01** — The app is `@HiltAndroidApp class App : Application()`; the single Activity is
`@AndroidEntryPoint`; every screen ViewModel is `@HiltViewModel` with `@Inject constructor` and is obtained with
`hiltViewModel()`. No other Android component is an entry point unless it genuinely needs injection.
*Why:* one Activity plus ViewModels covers a Compose app; extra entry points add generated code and lifecycle
surprises.

**DI-02** — Bindings are installed in `SingletonComponent`. There are no ViewModel-, Activity- or
Fragment-scoped Hilt modules; per-screen state belongs to the ViewModel itself, per-flow state to `Scopes`
(KERNEL-08).
*Why:* a single component keeps the graph flat and predictable; scoped components rarely pay for their
complexity in a single-activity Compose app.

**DI-03** — Constructor injection is the default. Field injection is allowed only on Android entry points
(`App`, the Activity) and only for the reasons in DI-14.
*Why:* constructor injection makes every class constructible in a plain JVM test without Hilt.

## 2. Where modules live

**DI-04** — A Hilt module lives in the module that owns the implementations it binds:
`<module>/src/main/java/…/<module>/di/<Name>Module.kt` (`XDomainModule` for a feature domain, `NetworkModule`
for an infra module, `LoggingModule` / `LifecycleModule` in the kernel). `:x-ui` modules have no Hilt modules.
`:app/di/` holds only (a) environment config providers (MOD-15) and (b) bindings that span two sibling modules
(MOD-19).
*Why:* bindings next to their implementations keep `internal` impls internal; the host only wires what nobody
else may see.

**DI-05** — Every module that declares an `@Inject` constructor, `@Module`, `@HiltViewModel` or `@Singleton` type
MUST apply the `{{CONVENTION_PREFIX}}.android.hilt` convention.
*Why:* KSP generates factories only in modules where it runs; a missing convention surfaces later as a
confusing "cannot be provided" error in `:app`.

## 3. Module shape

**DI-06** — Public surface is an **interface**; the implementation is `internal` (or at least not referenced
outside the module) and bound with `@Binds`. Shape:
```kotlin
@Module
@InstallIn(SingletonComponent::class)
internal abstract class OrdersDomainModule {
    @Binds abstract fun bindOrdersInteractor(impl: DefaultOrdersInteractor): OrdersInteractor
    @Binds abstract fun bindOrdersService(impl: RetrofitOrdersService): OrdersService

    companion object {
        @Provides @Singleton
        fun provideOrdersApi(@ApiRetrofit retrofit: Retrofit): OrdersApi = retrofit.create()
    }
}
```
A module with only `@Provides` functions is an `object`; its `@Provides` functions are public (BUILD-40).
*Why:* consumers depend on an interface they can fake; `@Binds` costs no generated factory.

**DI-07** — Every seam a test fakes (interactor, service, store, cache, clock, dispatcher, OS facility) is an
interface; pure stateless helpers (validators, mappers, policies) are concrete classes or `object`s used directly.
*Why:* interfaces where they buy a fake, concrete code where they would only add ceremony.

**DI-08** — Config classes for injection are `data class`es — never a `@JvmInline value class` over a primitive
(BUILD-37). Environment configs have **no default values** and are set in exactly one place (MOD-15); module
tuning configs MAY be defaulted by their owner.
*Why:* a missing environment binding must fail the build, not fall back to a placeholder URL.

**DI-09** — A module KDoc lists what it deliberately leaves **unbound** (consumer-declared ports the host binds,
MOD-19).
*Why:* without it the next agent "fixes" the missing binding inside the feature and creates the sibling edge the
port exists to avoid.

## 4. Qualifiers, scopes, dispatchers

**DI-10** — Each infra module (and any module that owns a long-lived scope or its own client) declares its
qualifiers in `di/Qualifiers.kt`:
```kotlin
@Qualifier @Retention(AnnotationRetention.BINARY) annotation class ApiClient      // OkHttpClient
@Qualifier @Retention(AnnotationRetention.BINARY) annotation class ApiRetrofit    // Retrofit
@Qualifier @Retention(AnnotationRetention.BINARY) annotation class AuthScope      // CoroutineScope
@Qualifier @Retention(AnnotationRetention.BINARY) annotation class MediaIoDispatcher // CoroutineDispatcher
```
Qualify every OkHttp client, Retrofit, app-lifetime `CoroutineScope`, and module-private dispatcher. A per-screen
config that another screen might also need (e.g. a `PagingConfig`) is qualified per consumer too.
*Why:* qualifiers make ownership explicit and let two modules provide the same type without colliding; they
also make the "which client does this call use?" question answerable by reading the signature.

**DI-11** — App-lifetime scopes are provided `@Singleton` as `CoroutineScope(SupervisorJob() + <dispatcher>)` under
the owning module's qualifier. `GlobalScope` and ad-hoc `CoroutineScope(...)` inside classes are forbidden.
*Why:* `SupervisorJob` keeps one failing child from cancelling every other job on the scope; an injected scope
can be replaced by a test scope driven by virtual time.

## 5. Collisions and optional sets

**DI-12** — **No duplicate unqualified bindings.** When a type is provided by more than one module, every provider
but at most one is qualified (`@ApiRetrofit Retrofit`), and shared singletons that must be identical (a single
`Json` configuration) are provided **once** and reused.
*Why:* two unqualified `Retrofit` or `Json` providers compile in their own modules and fail only when `:app`
aggregates them — the error points at the host, not at the cause.

**DI-13** — A `Set<T>` that may legitimately be empty in some build variant or installation (plugin drivers,
optional contributors from Recommended components) is declared with `@Multibinds` in the module that consumes
it; contributors add with `@IntoSet`.
```kotlin
@Module @InstallIn(SingletonComponent::class)
internal abstract class InputModule {
    @Multibinds abstract fun drivers(): Set<InputDriver>   // may be empty: no vendor module installed
}
```
*Why:* without `@Multibinds`, an empty set is a missing binding and the build fails in exactly the
configuration that did not install the optional module (MOD-03).

## 6. Eager singletons

**DI-14** — Background machinery that must start at process start (foreground watch, a polling cache, an event
filter that must be registered before the first request, a stale-file sweeper) is a `@Singleton` that starts its
work in `init {}` on its own injected scope, and is **field-injected into `App` purely so it exists**:
```kotlin
@HiltAndroidApp
class App : Application() {
    // Injected to exist: constructed during super.onCreate(), before any screen.
    @Inject lateinit var foregroundWatch: AppForegroundWatch
}
```
Objects bound to the Activity lifecycle (an exclusive hardware claim, a user-interaction tracker fed from
`onUserInteraction`) are injected into the Activity and registered as `DefaultLifecycleObserver`s there.
Each such field carries a comment saying why it must be eager.
*Why:* a lazily constructed singleton starts whenever the first screen happens to touch it, so its behaviour
depends on navigation order; an event registered late misses events that already happened.

**DI-15** — Feature registration with the navigation registry is **explicit** in `App.onCreate()`, not done
through DI (ADR-0003).
*Why:* explicit calls are where host-supplied seams (MOD-18) are filled; the multibinding path is the scale-up
option, recorded in the ADR.

## 7. Testing

**DI-16** — JVM unit tests construct the class under test directly with fakes; Hilt test components are not used
in unit tests.
*Why:* direct construction is faster, needs no generated code, and fails at compile time when a dependency is
added — which is the moment the test should be updated.
